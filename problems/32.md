# 🧩 Problem #32 – Longest Valid Parentheses

**Difficulty:** Hard    
**Topics:** `String`, `Stack`, `Dynamic Programming`   
**Link:** https://leetcode.com/problems/longest-valid-parentheses/

---

## 📝 Problem Summary

Given a string containing only `(` and `)`, return the length of the longest substring that forms valid, well-formed parentheses.

For example:

* `(()` → `2`
* `)()())` → `4`
* `""` → `0`

The important word is **substring** — the valid parentheses must be contiguous.

---

## 💡 Core Insight

A valid parentheses substring has an equal number of opening and closing brackets:

`(` → `+1`
`)` → `-1`

So while scanning the string, we can maintain:

* `openBracket`
* `closeBracket`

Whenever:

`openBracket === closeBracket`

we have a balanced section.

### But balance alone isn't enough.

Consider:

`())`

After reading `()`:

`open = 1, close = 1`

so we have a valid substring of length `2`.

Then we encounter another `)`:

`open = 1, close = 2`

Now there are more closing brackets than opening brackets.

That means the current section **can never become valid again**, so we reset both counters.

This gives us the first important rule:

> If scanning left → right and `closeBracket > openBracket`, the current segment is permanently invalid and can be discarded.

---

## 🎯 Pattern Recognition

The solution is based on **counting balance** rather than explicitly matching brackets.

For a left-to-right scan:

* `open === close` → balanced → possible valid substring
* `close > open` → impossible to recover → reset

However, there is a problem.

A left-to-right scan cannot detect every valid substring.

Consider:

`(()`

Counts from left to right:

| Character | Open | Close |
| --------- | ---: | ----: |
| `(`       |    1 |     0 |
| `(`       |    2 |     0 |
| `)`       |    2 |     1 |

We never get:

`open === close`

But the substring:

`()`

at the end is valid.

The problem is that there is an **extra opening bracket**, not an extra closing bracket.

So we need to scan in the opposite direction.

---

## 🚀 Evolution of Thought Process

### Step 1 — Count opening and closing brackets

The first natural idea is:

> If the number of `(` and `)` becomes equal, we have a valid section.

For example:

`(()())`

At the end:

`open = 3`
`close = 3`

Therefore length = `6`.

But this alone isn't enough.

---

### Step 2 — Reset when closing brackets exceed opening brackets

Consider:

`)()())`

Starting from the left:

```text
)
```

Immediately:

`close > open`

There is no possible way for a future character to fix this prefix because future characters are processed **after** it.

So we reset:

```text
open = 0
close = 0
```

Then we process the next segment:

`()()`

and find length `4`.

This handles strings where there are too many `)`.

---

### Step 3 — Discover the missing case

Now consider:

`(()`

There are too many `(`.

A left-to-right scan ends with:

```text
open = 2
close = 1
```

We never get equality.

But there is still a valid substring:

`()`

So the problem is symmetric.

If the problem is caused by **extra closing brackets**, scan left → right.

If the problem is caused by **extra opening brackets**, scan right → left.

---

### Step 4 — Reverse the perspective

When scanning right → left:

`(()`

becomes conceptually:

```text
) ( (
```

Now we count again.

In this direction, the invalid situation is:

```text
openBracket > closeBracket
```

because there are more `(` than `)` in the portion we're currently considering.

So we reset whenever:

```text
openBracket > closeBracket
```

This is exactly the mirror image of the first scan.

---

## 🔍 Detailed Reasoning

### Pass 1 — Left → Right

We count:

```text
openBracket
closeBracket
```

When:

```text
openBracket === closeBracket
```

we have a balanced substring.

Its length is:

```text
2 * openBracket
```

Why?

Because:

```text
openBracket === closeBracket
```

so the total number of brackets is:

```text
openBracket + closeBracket
= 2 * openBracket
```

### Why reset when `closeBracket > openBracket`?

Suppose we have:

```text
( ))
```

At some point:

```text
closeBracket > openBracket
```

There are more closing brackets than opening brackets.

No future `(` can repair the current substring because any future characters would create a **new extension**, while this prefix already contains an unmatched `)`.

Therefore, discard the current segment and start fresh.

---

### Pass 2 — Right → Left

Now we reverse the logic.

We again count:

```text
openBracket
closeBracket
```

Whenever:

```text
openBracket === closeBracket
```

we found a balanced substring.

But now the impossible situation is:

```text
openBracket > closeBracket
```

There are too many opening brackets relative to the closing brackets available to their right.

So we reset.

---

## 🧩 Approach 1 — My Solution

Your March 2025 solution uses **two directional counting passes**.

```ts
function longestValidParentheses(s: string): number {
  if(s.length < 2) return 0;
  
  let maxValidbrackets = 0;
  let openBracket = 0;
  let closeBracket = 0;
  
  // left to right
  for(let i=0; i<s.length; i++){
      if(s[i] === "(") openBracket++;
      else closeBracket++;
  
      if(openBracket === closeBracket){
          maxValidbrackets = Math.max(maxValidbrackets, 2 * openBracket);
      }
  
      if(closeBracket > openBracket){
          openBracket = 0;
          closeBracket = 0;
      }
  }
  
  // right to left
  openBracket = 0;
  closeBracket = 0;
  
  for(let i=s.length - 1; i>=0; i--){
      if(s[i] === "(") openBracket++;
      else closeBracket++;
  
      if(openBracket === closeBracket){
          maxValidbrackets = Math.max(maxValidbrackets, 2 * openBracket);
      }
  
      if(openBracket > closeBracket){
          openBracket = 0;
          closeBracket = 0;
      }
  }
  
  return maxValidbrackets;
}
```

### What is good about your solution?

The interesting part is that you didn't need a stack, DP array, or extra data structure.

You identified a useful symmetry:

```text
Left → Right
extra ')' → impossible → reset

Right → Left
extra '(' → impossible → reset
```

Together, these two scans cover both types of imbalance.

### Complexity

**Time:** `O(n)`

There are two complete scans:

```text
O(n) + O(n) = O(n)
```

**Space:** `O(1)`

Only a few counters are used.

## 🧩 Approach 2 — Stack-Based Alternative

A common alternative is to use a stack of indices.

The important idea is to store the index of the most recent position that acts as a **boundary**.

Conceptually:

```ts
function longestValidParentheses(s: string): number {
  const stack: number[] = [-1];
  let maxLength = 0;
  
  for (let i = 0; i < s.length; i++) {
      if (s[i] === "(") {
          stack.push(i);
      } else {
          stack.pop();
  
          if (stack.length === 0) {
              stack.push(i);
          } else {
              maxLength = Math.max(
                  maxLength,
                  i - stack[stack.length - 1]
              );
          }
      }
  }
  
  return maxLength;
}
```

### Why is this an improvement?

Not necessarily because it is faster.

Both approaches are:

**Time:** `O(n)`
**Space:** `O(1)` for your approach vs `O(n)` for the stack approach.

The stack solution is arguably easier to generalize when we need to know **where matching parentheses occur**, because it preserves indices.

Your solution is more space-efficient because it only cares about the **length**, not the exact positions.

So this is an important distinction:

> The stack solution is not an optimization of your algorithm's complexity. It is an alternative representation that makes index relationships explicit.

For this specific problem, your two-pass solution has the advantage of constant extra space.

## ⚖️ Correctness

The two scans work because every invalid segment has one of two possible directional problems.

### Case 1 — Too many `)`

Example:

`)()())`

While scanning left → right:

```text
close > open
```

means the current segment cannot form a valid substring extending across that position.

So we reset.

---

### Case 2 — Too many `(`

Example:

`(()`

While scanning left → right, we cannot finish a balanced segment because:

```text
open > close
```

But scanning from the opposite direction exposes the valid suffix.

During the reverse scan:

```text
open > close
```

means the current reverse segment cannot be balanced, so we reset.

Therefore, the two scans handle both possible unmatched-bracket directions.

---

## ⏱️ Complexity Analysis

**Time:** `O(n)`

Two linear scans:

```text
O(n) + O(n) = O(n)
```

**Space:** `O(1)`

Only:

```text
openBracket
closeBracket
maxValidbrackets
```

are maintained.

## 🏆 Key Takeaways

### 1. Balanced counts are useful, but not sufficient by themselves

Having:

```text
open === close
```

tells us that the current section is balanced.

But we also need to know whether the section became invalid before reaching that point.

---

### 2. The direction of scanning matters

This is the key insight you had in your old solution:

```text
Left → Right
watch for extra ')'

Right → Left
watch for extra '('
```

That symmetry is the entire trick.

---

### 3. Reset only when recovery is impossible

Left → right:

```text
close > open
```

cannot be repaired by future characters within the current segment.

Right → left:

```text
open > close
```

cannot be repaired within the current reverse segment.

---

### 4. Two `O(n)` passes are still `O(n)`

Don't mentally classify this as `O(2n)` in a meaningful complexity sense.

The constant factor `2` is ignored:

```text
2n → O(n)
```

---

### 5. Your old solution is actually a nice example of symmetry

The most reusable mental model is:

```text
        Longest Valid Parentheses

              balanced?
             /          \
           YES           NO
            |             |
       record length    imbalance
                          |
             ┌────────────┴────────────┐
             ↓                         ↓
       Left → Right              Right → Left
       extra ')'                extra '('
          reset                    reset
```

## 📚 Pattern Learned

### Bidirectional Counting

When a one-directional counting approach misses cases because of an imbalance at one boundary, ask:

> "Can I scan from the opposite direction and make the imbalance condition symmetric?"

This is particularly useful when the problem has a natural left/right symmetry.

For parentheses:

```text
L → R : ')' is the dangerous character

R → L : '(' is the dangerous character
```
