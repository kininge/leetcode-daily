# 🧩 Problem #2089 – Find Target Indices After Sorting Array

**Difficulty:** Easy  
**Topics:** Array, Sorting, Counting  
**Link:** https://leetcode.com/problems/find-target-indices-after-sorting-array/

---

## 📝 Problem Summary

Given an integer array `nums` and a `target`, return all indices where `nums[i] === target` after sorting the array in non-decreasing order.

The returned indices must be in increasing order.

**Example**

- Input: `nums = [1, 2, 5, 2, 3]`, `target = 2`
- Sorted array: `[1, 2, 2, 3, 5]`
- Output: `[1, 2]`

## 💡 Core Insight

Sorting is not necessary to determine the target's final positions.

In a sorted array:

1. Every element smaller than `target` appears before it.
2. All occurrences of `target` appear consecutively.
3. The number of smaller elements determines the first target index.
4. The number of target occurrences determines how many consecutive indices to return.

Therefore:

- `firstTargetIndex = smallerThanTargetCount`
- `lastTargetIndex = smallerThanTargetCount + targetCount - 1`

We can calculate both counts in a single pass and generate the answer directly.

## 🎯 Pattern Recognition

This problem demonstrates **counting to determine sorted positions**.

When a problem asks about an element's position after sorting, ask yourself:

- Do I actually need the sorted array?
- Can I determine the element's position from the number of elements smaller than it?
- Can I determine its range from its frequency?

If the answer is yes, counting may eliminate the sorting step.

## 🚀 Evolution of Thought Process

### Approach 1 — Sort, Then Find

The most straightforward approach follows the problem statement literally:

1. Sort the array.
2. Traverse the sorted array.
3. Collect every index where the element equals `target`.
4. Return the collected indices.

This works, but sorting performs more work than necessary.

### Approach 2 — Count, Then Calculate Positions (My Solution)

Instead of rearranging the array, count:

- The number of elements smaller than `target`.
- The number of occurrences of `target`.

The first count tells us where the target block starts. The second tells us the length of that block.

This avoids sorting entirely and improves the time complexity from `O(n log n)` to `O(n)`.

## 🔍 Detailed Reasoning

Consider:

`nums = [1, 2, 5, 2, 3]`, `target = 2`

**Step 1: Count smaller elements and target occurrences.**

| Element | Smaller than 2? | Equal to 2? |
|---|---|---|
| 1 | Yes | No |
| 2 | No | Yes |
| 5 | No | No |
| 2 | No | Yes |
| 3 | No | No |

After traversing the array:

- `smallerThanTargetCount = 1`
- `targetCount = 2`

**Step 2: Calculate the target indices.**

The first target index is `1`, because one element must precede the target in sorted order.

The target appears twice, so the required indices are `1` and `2`.

**Final answer:** `[1, 2]`

## 🧩 Approach 1 — Sorting

### TypeScript Code

```typescript
function targetIndices(nums: number[], target: number): number[] {
    nums.sort((a, b) => a - b);

    const ans: number[] = [];

    for (let i = 0; i < nums.length; i++) {
        if (nums[i] === target) {
            ans.push(i);
        }
    }

    return ans;
}
```

### Explanation

1. Sort `nums` in ascending order using `(a, b) => a - b`.
2. Traverse the sorted array using index `i`.
3. Whenever `nums[i] === target`, add `i` to the result.
4. Return the result.

The indices are automatically in increasing order because we traverse from left to right.

### Complexity

**Time:** `O(n log n)` for sorting, plus `O(n)` for traversal. Overall, `O(n log n)`.

**Auxiliary space:** Depends on the JavaScript engine's sorting implementation.

**Output space:** `O(k)`, where `k` is the number of target occurrences.

**Trade-off:** Simple and intuitive, but sorting is unnecessary when we only need the target indices.

## 🧩 Approach 2 — My Counting Solution (Optimized)

### TypeScript Code

```typescript
function targetIndices(nums: number[], target: number): number[] {
    const ans: number[] = [];
    let targetCount = 0;
    let smallerThanTargetCount = 0;

    for (const num of nums) {
        if (num < target) {
            smallerThanTargetCount++;
        } else if (num === target) {
            targetCount++;
        }
    }

    for (
        let i = smallerThanTargetCount;
        i < smallerThanTargetCount + targetCount;
        i++
    ) {
        ans.push(i);
    }

    return ans;
}
```

### Explanation

**Pass 1: Count elements.**

- `smallerThanTargetCount` tells us the first target index.
- `targetCount` tells us how many target indices exist.

**Pass 2: Generate indices.**

Start at `smallerThanTargetCount` and continue until, but not including, `smallerThanTargetCount + targetCount`.

For the example:

- Start: `1`
- End boundary: `1 + 2 = 3`
- Generated indices: `1, 2`

If `targetCount` is zero, the second loop runs zero times, and the function returns an empty array automatically. Therefore, the explicit `if (targetCount > 0)` check is unnecessary.

### Complexity

**Time:** `O(n)` for counting plus `O(k)` for generating indices, giving `O(n + k) = O(n)`.

**Auxiliary space:** `O(1)`, excluding the output array.

**Output space:** `O(k)`.

**Trade-off:** Requires understanding why sorted positions can be derived from counts, but avoids sorting and is asymptotically faster.

## ⚖️ Correctness

### Why the sorting approach works

After sorting, the array is in non-decreasing order. Traversing it from index `0` to `n - 1` and collecting every index containing `target` returns exactly the required indices in increasing order.

### Why the counting approach works

Let:

- `s` be the number of elements strictly smaller than `target`.
- `k` be the number of occurrences of `target`.

In sorted order, exactly `s` elements must precede every occurrence of `target`. Therefore, the first target index is `s`.

Since all `k` occurrences are consecutive, their indices are:

`s, s + 1, ..., s + k - 1`

The algorithm generates precisely these indices. If `k = 0`, it generates none, returning an empty array.

Thus, the counting approach produces the same answer as sorting without constructing the sorted array.

## ⏱️ Complexity Analysis

| Criteria | Approach 1 — Sorting | Approach 2 — Counting |
|---|---|---|
| Time | `O(n log n)` | `O(n)` |
| Auxiliary space | Depends on sort implementation | `O(1)` |
| Output space | `O(k)` | `O(k)` |
| Sorts the input | Yes | No |
| Best use | When sorted order is needed | When only target indices are needed |

Here, `n` is the array length and `k` is the number of target occurrences.

## 🏆 Key Takeaways

- Do not automatically sort an array just because a problem mentions sorted order.
- Ask whether the required result can be calculated without constructing the sorted array.
- Counting elements smaller than a target determines its starting position in sorted order.
- Counting duplicates determines the length of the target's consecutive index range.
- A two-pass `O(n)` solution can be better than sorting when the sorted array itself is not required.
- Remember to distinguish auxiliary space from output space when analyzing complexity.

## 📚 Pattern Learned

**Counting instead of sorting**

Use this pattern when the required output depends only on an element's rank or position in sorted order, and those positions can be derived from counts.

Related ideas include frequency counting, rank calculation, order statistics, and prefix counts.
