# 🧩 Problem #1021 – Remove Outermost Parentheses

**Difficulty:** Easy  
**Topics:** `String`, `Stack`, `Math`     
**Link:** https://leetcode.com/problems/remove-outermost-parentheses/

---

## 📝 Problem Summary

Given a valid parentheses string `s`, split it into primitive valid parentheses strings and remove the outermost opening and closing parenthesis from each primitive.

A primitive is a nonempty valid parentheses string that cannot be split into two nonempty valid parentheses strings.

**Example:**

Input: `s = "(()())(())"`

Primitive decomposition:

`"(()())" + "(())"`

After removing the outermost parentheses:

`"()()" + "()"`

Output: `"()()()"`

---

## 💡 Core Insight

We don't need to split the string into primitive substrings.

Instead, maintain a counter representing the current **parentheses nesting depth**.

- When encountering `(`, increase the depth.
- When encountering `)`, decrease the depth.
- The opening parenthesis that changes the depth from `0` to `1` is an outermost opening parenthesis.
- The closing parenthesis that changes the depth from `1` to `0` is an outermost closing parenthesis.

Both must be excluded from the result.

**The key trick:** Update the counter first, then decide whether to keep the current character. This allows one condition to identify each outermost parenthesis.

---

## 🎯 Pattern Recognition

Whenever a problem asks us to identify matching or nested parentheses, consider tracking the **balance or depth**.

The depth tells us where we are relative to the current primitive:

- `0`: Outside any primitive.
- `1`: At the outermost level of a primitive.
- `2` or more: Inside the primitive.

We can recognize primitive boundaries without storing a stack because the input is guaranteed to be a valid parentheses string.

## 🚀 Evolution of Thought Process

### Step 1 — Understand primitive boundaries

Consider:

`"(()())(())"`

There are two primitives:

- `"(()())"`
- `"(())"`

Every primitive contributes one outermost opening and one outermost closing parenthesis that must be removed.

### Step 2 — Track nesting depth

Use a variable `count`.

For every opening parenthesis, increase it. For every closing parenthesis, decrease it.

The depth returns to `0` whenever a primitive finishes.

### Step 3 — Recognize the outer parentheses

My original approach uses two conditions:

- `isReducing && count === 0`: The current character is `)`, and the primitive has just ended.
- `!isReducing && count === 1`: The current character is `(`, and the depth has just entered a primitive.

If either condition is true, skip the character. Otherwise, append it to the answer.

### Step 4 — Why update before checking?

For an opening parenthesis, the updated depth becomes `1` when it is outermost.

For a closing parenthesis, the updated depth becomes `0` when it is outermost.

This ordering makes both boundary checks straightforward.

---

## 🔍 Detailed Reasoning

Let's walk through the two conditions in the original solution.

### Condition 1: Outermost closing parenthesis

`isReducing && count === 0`

When the current character is `)`, `count` decreases first.

If the resulting depth is `0`, we have closed the entire primitive. Therefore, this closing parenthesis is the outermost closing parenthesis and must be skipped.

### Condition 2: Outermost opening parenthesis

`!isReducing && count === 1`

When the current character is `(`, `count` increases first.

If the resulting depth is `1`, we have just entered a primitive from outside it. Therefore, this opening parenthesis is the outermost opening parenthesis and must be skipped.

### Why not split the string?

Splitting would introduce unnecessary work and additional intermediate strings. A single pass with a counter solves the problem directly.

|---|---:|---|---|
| `(` | 1 | Skip outer opening | `""` |
| `(` | 2 | Keep | `"("` |
| `)` | 1 | Keep | `"()"` |

| `)` | 1 | Keep | `"()()"` |
| `)` | 0 | Skip outer closing | `"()()"` |

Notice that the counter returns to `0` after processing the final character. The primitive is complete, and both of its outer parentheses have been removed.

## 🧩 Approach 1 — My Solution

### Idea

Use a nesting-depth counter and two conditions to skip the outermost opening and closing parentheses.

```ts
function removeOuterParentheses(s: string): string {
    let count = 0;
    let ans = '';

    for (const bracket of s) {
        const isReducing: boolean = bracket === ')';

        count += isReducing ? -1 : 1;

        const condition1 = isReducing && count === 0;
        const condition2 = !isReducing && count === 1;

        if (!condition1 && !condition2) {
            ans += bracket;
        }
    }

    return ans;
}
```

### Complexity

**Time:** \(O(n)\) — one pass through the input.

**Auxiliary space:** \(O(1)\), excluding the output string.

**Output space:** \(O(n)\).

### What is good about my solution?

- No stack is required.
- No primitive substrings need to be created.
- Both outer parentheses are detected using the updated depth.
- The code is a single pass and easy to follow.

## 🧩 Approach 2 — Simplified Equivalent Solution

The original solution is correct. We can make the conditions more compact by handling the opening and closing parentheses separately.

The idea is to append an opening parenthesis only when we are already inside a primitive, and append a closing parenthesis only when the depth is greater than one before decreasing it.

```ts
function removeOuterParentheses(s: string): string {
    let depth = 0;
    let ans = '';

    for (const bracket of s) {
        if (bracket === '(') {
            if (depth > 0) {
                ans += bracket;
            }
            depth++;
        } else {
            depth--;
            if (depth > 0) {
                ans += bracket;
            }
        }
    }

    return ans;
}
```

### Why is this an improvement?

It removes the temporary Boolean and the two condition variables. Each branch expresses the decision directly.

However, this is primarily a readability improvement, **not an asymptotic performance improvement**. Both approaches run in \(O(n)\) time and use \(O(1)\) auxiliary space, excluding the output.

---

## ⚖️ Correctness

The algorithm maintains `count` as the current nesting depth.

For every primitive:

1. Its first opening parenthesis changes the depth from `0` to `1`. The algorithm skips it.
2. Every opening parenthesis inside the primitive increases the depth beyond `1`, so it is retained.
3. Every closing parenthesis that leaves the depth above `0` is internal and retained.
4. Its final closing parenthesis changes the depth from `1` to `0`. The algorithm skips it.

Since the input is guaranteed to be a valid parentheses string, each primitive begins at depth `0` and ends at depth `0`. Thus, exactly the two outermost parentheses of every primitive are removed, while all internal parentheses remain in their original order.

Therefore, the algorithm returns the required result.

---

## ⏱️ Complexity Analysis

Let \(n\) be the length of `s`.

**Time:** \(O(n)\)

Every character is visited exactly once, and each iteration performs constant-time operations.

**Auxiliary space:** \(O(1)\)

Only a constant number of variables are maintained, excluding the output.

**Output space:** \(O(n)\)

The resulting string can contain up to \(n\) characters.

## 🏆 Key Takeaways

1. A nesting-depth counter can replace a stack when we only need to track valid parentheses depth.
2. The order of updating state and checking conditions matters.
3. Depth `1` after processing `(` identifies an outermost opening parenthesis.
4. Depth `0` after processing `)` identifies an outermost closing parenthesis.
5. A correct solution can often be simplified for readability without changing its time or space complexity.
6. Avoid creating intermediate substrings when a single-pass scan can solve the problem.

## 📚 Pattern Learned

**Pattern: Parentheses Depth / Balance Counting**

Use this pattern when a problem involves valid parentheses and requires identifying nesting levels or primitive boundaries.

The broader lesson is to ask:

*What state changes when I process each character, and can that state identify the characters I need to keep or discard?*

Here, the nesting depth provides all the information we need.
