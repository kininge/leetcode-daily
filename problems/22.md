# 🧩 Problem #22 – Generate Parentheses

**Difficulty:** Medium  
**Topics:**`Backtracking`, `Recursion`, `String`  
**Link:** https://leetcode.com/problems/generate-parentheses/

---

## 📝 Problem Summary

Given `n` pairs of parentheses, generate every possible combination of parentheses that is **well-formed**.

For example, when `n = 3`:

```txt
["((()))","(()())","(())()","()(())","()()()"]
```

A valid parentheses string must satisfy:

- It contains exactly `n` opening parentheses `(`.
- It contains exactly `n` closing parentheses `)`.
- At every point, we must have enough opening parentheses to match every closing parenthesis used so far.
- At the end, all parentheses must be balanced.

---

## 💡 Core Insight

This is a **backtracking** problem.

While constructing the answer, at every position we have two possible choices:

```txt
1. Add `(`
2. Add `)`
```

But both choices are not always valid.

We need to track how many unmatched opening parentheses currently exist.

In the final solution, this is represented by:

```txt
openCount
```

where:

```txt
openCount = number of `(` used - number of `)` used
```

Therefore:

- We can add `(` while fewer than `n` opening parentheses have been used.
- We can add `)` only when `openCount > 0`.

The second rule is especially important because it prevents invalid prefixes such as:

```txt
")("
```

---

## 🎯 Pattern Recognition

The problem asks us to:

- Generate **all possible combinations**.
- Reject invalid partial combinations.
- Continue making choices until a complete valid combination is formed.

That strongly suggests **backtracking with pruning**.

The important question is not simply:

> "What are all possible strings?"

It is:

> "Which choices are valid at the current state?"

Once invalid branches are prevented from being explored, the recursion naturally generates only valid possibilities.

## 🚀 Evolution of Thought Process

### Step 1 — Initial Idea

The original solution from **20 Dec 2024 / 12 Jan 2025** was already using the correct underlying idea.

It recursively tried both possibilities:

```txt
generate(paranthesis + "(", count + 1);
generate(paranthesis + ")", count - 1);
```

Here, `count` represented the current balance of parentheses.

The branch was discarded whenever:

```txt
count < 0
```

So the thinking was:

> Try both choices, and stop exploring a branch once it becomes invalid.

This is a valid backtracking strategy.

---

### Step 2 — The Improvement

The newer solution changes the question from:

> "Can I generate this and later discover that it is invalid?"

to:

> "Is this choice valid before I generate it?"

Instead of always generating both branches:

```txt
generate("(")
generate(")")
```

we explicitly check whether each choice is legal.

For example:

```txt
if (openCount < n) {
    // `(` is allowed
}

if (openCount > 0) {
    // `)` is allowed
}
```

This makes the pruning rules much clearer.

---

### Step 3 — Better State Representation

The old solution starts with:

```txt
generate("(", 1);
```

This special-cases the first opening parenthesis.

The newer solution starts from the natural empty state:

```txt
generator(0, 0, "");
```

Now the recursion handles **every character using the same rules**.

There is no special handling for the first character.

This makes the recursive model cleaner and easier to reason about.

## 🔍 Detailed Reasoning

There are three pieces of state in the current solution:

```txt
size
openCount
bracket
```

### `size`

Number of characters currently placed in `bracket`.

The final string must contain exactly:

```txt
2 * n
```

characters.

Therefore, once:

```txt
size === 2 * n
```

we have reached a complete candidate.

---

### `openCount`

This represents the current parenthesis balance:

```txt
openCount = unmatched opening parentheses
```

For example:

```txt
"((()" -> openCount = 3
"(()"  -> openCount = 1
"()"   -> openCount = 0
```

It can never become negative.

If `openCount === 0`, there is currently nothing available to close.

Therefore:

```txt
if (openCount > 0)
```

is exactly the condition for adding `)`.

---

### `bracket`

This is the string being constructed along the current recursion path.

Each recursive call adds either:

```txt
"("
```

or:

```txt
")"
```

until the string reaches length `2 * n`.

## 🧪 Dry Run

Consider:

```txt
n = 2
```

Start:

```txt
size = 0
openCount = 0
bracket = ""
```

### Step 1

We can add `(` because:

```txt
openCount < n
0 < 2
```

State:

```txt
"("
openCount = 1
```

We cannot add `)` before this because `openCount` was `0`.

---

### Step 2

From `"("`, both choices are possible.

Add `(`:

```txt
"(("
openCount = 2
```

Or add `)`:

```txt
"()"
openCount = 0
```

From `"(("`, we cannot add another `(` because we already used both opening parentheses.

So we must close:

```txt
"(()"
openCount = 1
```

Then:

```txt
"(())"
openCount = 0
```

This becomes one answer.

The other branch eventually produces:

```txt
"()()"
```

Therefore:

```txt
["(())", "()()"]
```

## 🧩 Approach 1 — My Original Solution

Your Jan 2025 solution:

```ts
var generateParenthesis = function(n) {
    
    const answers = [];

    function generate(paranthesis, count){
        if(count >= 0){
            if(paranthesis.length < (n*2)){

                if(count >= 0 ){
                    generate(paranthesis+"(", count+1);
                    generate(paranthesis+")", count-1);
                }
            } else {
                if(count === 0){
                    answers.push(paranthesis);
                }
            }
        }
    }

    generate("(", 1);

    return answers;
};
```

### Idea

The `count` variable represents the current parenthesis balance.

For example:

```txt
"("  -> count = 1
"()" -> count = 0
"(()" -> count = 1
```

Every recursive call tries both:

```txt
count + 1
count - 1
```

If `count` becomes negative, the branch is invalid and is discarded.

At the end, only strings with:

```txt
count === 0
```

are added.

### What was good

The fundamental algorithm was already correct:

- Recursion
- Backtracking
- Balance tracking
- Pruning invalid branches
- Final balance check

So this was **not a wrong approach**.

The main issue was clarity of the invariant and unnecessary exploration.

## 🧩 Approach 2 — Improved Current Solution

Your current solution:

```ts
function generateParenthesis(n: number): string[] {
    const ans: string[] = [];

    function generator(
        size: number,
        openCount: number,
        bracket: string
    ) {
        if (size === 2 * n) {
            if (openCount === 0) {
                ans.push(bracket);
            }
            return;
        }

        // Add opening bracket
        if (openCount < n) {
            generator(
                size + 1,
                openCount + 1,
                bracket + "("
            );
        }

        // Add closing bracket
        if (openCount > 0) {
            generator(
                size + 1,
                openCount - 1,
                bracket + ")"
            );
        }
    }

    generator(0, 0, "");

    return ans;
}
```

### Why this is an improvement

The biggest improvement is **where the validation happens**.

### Original

The old solution essentially says:

```txt
"Try both choices, then reject the branch if the balance becomes invalid."
```

### Current

The new solution says:

```txt
"Only make a choice if that choice is valid."
```

That makes the invariant explicit.

---

### Improvement 1 — No invalid `)` branch

Old thinking:

```txt
generate(")", count - 1);
```

and then later:

```txt
if (count < 0) stop;
```

New thinking:

```txt
if (openCount > 0) {
    // Only now generate ")"
}
```

We don't even create the invalid branch.

---

### Improvement 2 — No special first character

Old:

```txt
generate("(", 1);
```

Current:

```txt
generator(0, 0, "");
```

The empty state is the natural root of the recursion.

Every subsequent decision follows exactly the same rules.

---

### Improvement 3 — More meaningful state

The current code separates:

```txt
size
openCount
bracket
```

This makes each piece of state easier to understand.

Most importantly, `openCount` has a clear invariant:

```txt
openCount >= 0
```

and:

```txt
openCount <= n
```

## ⚖️ Correctness

The algorithm is correct because it maintains two important invariants.

### Invariant 1 — Never use more than `n` opening parentheses

We only add `(` when:

```txt
openCount < n
```

Therefore, at most `n` opening parentheses are used.

---

### Invariant 2 — Never close without an unmatched opening parenthesis

We only add `)` when:

```txt
openCount > 0
```

Therefore:

```txt
openCount >= 0
```

throughout the recursion.

This guarantees that no generated prefix contains an unmatched closing parenthesis.

---

### Final State

When:

```txt
size === 2 * n
```

the string contains exactly `2n` parentheses.

If additionally:

```txt
openCount === 0
```

then the number of opening and closing parentheses is equal.

Combined with the invariant that `openCount` never became negative, the complete string is well-formed.

Therefore every added answer is valid.

Backtracking explores all valid choices, so every valid combination is generated.

---

## ⏱️ Complexity Analysis

The number of valid parentheses combinations is the `n`th Catalan number:

```txt
Cₙ = 1 / (n + 1) × C(2n, n)
```

Every result contains `2n` characters.

Therefore:

**Time:** `O(Cₙ × n)`

The output itself contains `Cₙ` strings of length `2n`, so this output cost is unavoidable.

**Space:** `O(Cₙ × n)` for the returned results, plus `O(n)` recursion depth.

If we exclude the output:

**Auxiliary Space:** `O(n)`

## 🏆 Key Takeaways

1. **Generate-all + validity constraints → think backtracking.**

2. Don't just ask:
   > "What choices can I make?"

   Also ask:
   > "Which choices are valid right now?"

3. `openCount` is a useful invariant:
   
   ```txt
   openCount = unmatched "("
   ```

4. A closing parenthesis is valid only when:
   
   ```txt
   openCount > 0
   ```

5. An opening parenthesis is valid only while:
   
   ```txt
   openCount < n
   ```

6. Your old solution had the correct algorithm. The newer solution is better mainly because it **moves validation before generation**, making the invariant explicit and avoiding invalid recursive branches.

7. Starting recursion from the empty state is usually cleaner than special-casing the first element.

## 📚 Pattern Learned

### Backtracking with Valid-State Pruning

General pattern:

```ts
function backtrack(state) {
    if (isComplete(state)) {
        save(state);
        return;
    }

    for (const choice of choices) {
        if (isValid(choice, state)) {
            apply(choice);
            backtrack(state);
            undo(choice);
        }
    }
}
```

For Generate Parentheses:

```txt
Choices:
    "("
    ")"

Validity:
    "(" -> openCount < n
    ")" -> openCount > 0

Complete:
    length === 2 * n
```

This pattern appears frequently in:

- Generate Parentheses
- Permutations
- Combinations
- Subsets
- N-Queens
- Sudoku
- Word Search
- Combination Sum

| Criteria | Approach 1 — Original | Approach 2 — Improved |
| --------- | ---------- | ---------- |
| Core Idea | Generate both choices and prune invalid balance | Generate only valid choices |
| State | `parenthesis`, `count` | `size`, `openCount`, `bracket` |

Your 2024/2025 solution already had the right backtracking intuition:

```txt
"Try both possibilities and stop when the balance becomes invalid."
```

Your current solution improves that mental model into:

```txt
"Only explore states that can still lead to a valid answer."
```
